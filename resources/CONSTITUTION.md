# Project Constitution / 项目宪法

**版本：v1.0**  
**状态：项目执行防跑偏基准文件**  
**适用范围：项目负责人、开发者、Codex、AI Agent、自动化任务及任何后续协作者**

---

## 第一条：最高目标

本项目的最高目标不是“看起来完整”，而是：

> **让核心能力在真实运行环境中可靠执行，并能够被实际用户稳定使用。**

任何开发、修改、重构、设计、文档、部署或研究工作，都必须能够解释它如何直接或间接推进这一目标。

如果无法解释，则默认不应成为当前优先事项。

---

## 第二条：真实性原则

项目必须严格区分以下四种状态：

1. **已运行（Running）**  
   已经在真实运行环境中成功执行，并有可验证结果。

2. **已实现（Implemented）**  
   代码已经存在，但尚未证明在真实环境中成功执行。

3. **已设计（Designed）**  
   已有架构、接口、流程或设计，但功能尚未完整实现。

4. **已规划（Planned）**  
   仅存在于文档、任务列表、讨论或设想中。

禁止将：

- 有代码 = 已运行
- 有 API = 能力可用
- 有 UI = 功能完成
- 有文档 = 系统支持
- Demo 成功 = 生产环境稳定
- 单次成功 = 已完成

任何状态描述必须基于证据，而不是推测。

---

## 第三条：运行环境优先原则

在判断系统能力时：

> **真实运行环境的状态高于代码仓库、文档和设计。**

如果代码与运行环境不一致，以运行环境为准。

如果文档与运行环境不一致，以运行环境为准。

如果开发者认为某能力“应该可以运行”，但没有实际执行证据，则该能力仍视为未验证。

---

## 第四条：当前最高优先级

当前阶段必须按照以下顺序推进：

### P0 — 审计真实运行状态

首先确认：

- 当前服务器实际运行了什么
- 当前 Agent 实际可以做什么
- 哪些能力已经真正执行成功
- 哪些能力只是存在于代码中
- 哪些能力完全没有接入
- 哪些能力运行失败或不稳定

必须形成明确的：

**Running / Implemented / Designed / Planned**

能力矩阵。

### P1 — 打通最短真实执行链路

在扩展系统之前，必须优先找到：

> **从用户输入 → Agent 判断 → Tool/Action 执行 → 真实结果返回**

的最短闭环。

优先保证一个完整能力真正工作，而不是同时开发十个半完成能力。

### P2 — 提升可靠性

核心链路打通后，优先处理：

- 错误处理
- 超时
- 重试
- 日志
- 权限
- 状态同步
- 数据一致性
- 环境变量
- Tool 调用失败
- Agent 错误判断

### P3 — 扩展能力

只有在核心闭环稳定之后，才允许增加：

- 新 Tool
- 新 Agent 能力
- 新自动化
- 新第三方服务
- 新模型
- 新复杂工作流

### P4 — 产品层优化

只有前述层级基本稳定后，才进入：

- UI 优化
- UX 重构
- 动画
- 页面美化
- 品牌视觉
- 大规模前端重写

### P5 — 外围包装

以下内容默认不是当前核心开发优先级：

- 专利包装
- 融资材料
- 宣传页面
- PR 内容
- 大规模架构包装
- 为未来规模提前设计的复杂基础设施

除非负责人明确改变优先级。

---

## 第五条：最短路径原则

当存在多个解决方案时，优先选择：

> **最短能够证明真实能力成立的路径。**

不要因为“以后可能需要”而提前建设复杂系统。

默认禁止：

- 过度抽象
- 过度模块化
- 提前微服务化
- 提前多云
- 提前 Kubernetes
- 提前构建复杂权限系统
- 提前建立大规模事件架构
- 为尚不存在的流量优化
- 为假设中的未来需求重构核心系统

除非已经存在明确、当前、可验证的需求。

---

## 第六条：禁止范围漂移

任何任务执行过程中，不得擅自把任务扩大。

例如：

原任务：

> 修复 Agent 无法调用某 Tool。

禁止未经允许自动扩大成：

> 重构整个 Agent 架构。

原任务：

> 检查 EC2 上当前运行状态。

禁止扩大成：

> 迁移到新的云平台。

原任务：

> 修复 API 调用。

禁止扩大成：

> 重写前端 UI。

发现更大的问题可以记录，但：

> **发现问题 ≠ 自动获得修改权限。**

---

## 第七条：问题分离原则

执行任务时必须区分：

### A. 当前阻塞问题

直接阻止当前目标完成的问题。

必须优先解决。

### B. 相关问题

会影响稳定性，但不会立即阻塞当前目标。

记录后安排。

### C. 潜在问题

理论上可能发生，但目前没有证据。

不得因为潜在问题中断当前任务。

---

## 第八条：不得绕过验证

任何关键修改完成后必须验证。

验证优先级：

1. 真实运行环境执行
2. 集成测试
3. API / Tool 实际调用
4. 自动测试
5. 静态代码检查

仅通过 lint、build 或单元测试不能证明系统功能已经完成。

---

## 第九条：完成定义

一个功能只有满足以下条件才能标记为 **DONE**：

- 代码已经实现
- 已部署到目标运行环境
- 实际调用成功
- 输入输出符合预期
- 失败路径可理解
- 没有阻断级错误
- 有最低限度日志或验证证据

否则必须使用：

- IMPLEMENTED
- PARTIAL
- BLOCKED
- UNVERIFIED

之一。

禁止虚假 DONE。

---

## 第十条：证据优先原则

任何关于系统状态的重要判断必须尽量附带证据，例如：

- 命令输出
- 日志
- API response
- HTTP status
- Tool execution result
- 数据库记录
- 截图
- 测试结果
- Deployment ID
- Commit
- Timestamp

“应该”“看起来”“理论上”“代码里有”不能作为完成证据。

---

## 第十一条：Codex / AI Agent 行为规则

任何参与项目的 Codex 或 AI Agent 必须遵守以下行为：

### 执行前

先确定：

- 当前目标是什么
- 当前阻塞是什么
- 需要查看哪些真实状态
- 哪些修改是必要的

不得直接假设系统状态。

### 执行中

优先：

1. Inspect
2. Verify
3. Diagnose
4. Modify
5. Test
6. Re-verify

不得跳过 Inspect 和 Verify 直接重构。

### 执行后

必须报告：

- 看到了什么
- 修改了什么
- 实际验证了什么
- 仍然没有验证什么
- 是否存在新的 blocker

---

## 第十二条：禁止“顺手重构”

除非重构是解决当前问题的必要条件，否则不得在修复过程中：

- 重命名大量文件
- 调整目录结构
- 更换框架
- 重写大量已有代码
- 修改无关 API
- 修改无关数据库结构
- 更换部署方式
- 更换模型供应商
- 更换基础设施

“代码更漂亮”不是充分理由。

---

## 第十三条：依赖控制

新增任何重要依赖前必须回答：

1. 为什么现有能力不能完成？
2. 新依赖解决什么明确问题？
3. 是否增加运行复杂度？
4. 是否增加供应商锁定？
5. 是否增加成本？
6. 是否增加新的故障点？

如果收益不明显大于复杂度，不应引入。

---

## 第十四条：架构服从产品事实

系统架构必须由实际需求驱动。

不得为了：

- 技术先进
- 架构漂亮
- 使用热门技术
- 展示工程复杂度

而增加系统复杂度。

架构的价值在于：

> **减少失败，提高执行成功率。**

---

## 第十五条：核心链路保护

一旦核心执行链路稳定：

> 用户 → Agent → Tool → Action → Result

任何修改不得破坏该链路。

涉及核心链路的修改必须优先进行 regression verification。

---

## 第十六条：单一事实来源

系统必须逐步形成明确的 Single Source of Truth。

对于：

- Agent capability
- Tool registration
- Runtime configuration
- Environment
- Deployment
- API endpoint
- Feature status

不得长期存在多个互相冲突的描述。

如果发现冲突，应优先识别真实运行状态，再更新文档。

---

## 第十七条：文档必须追随事实

文档是系统事实的记录，不是系统事实本身。

如果文档描述的能力不存在，应修改文档。

不得为了符合文档而假装能力存在。

---

## 第十八条：禁止为了 Demo 破坏系统

Demo 可以简化，但不得：

- hardcode 假结果并声称是真实执行
- 绕过核心逻辑制造成功
- 隐藏关键错误
- 将 mock 数据描述为真实数据
- 使用人工操作冒充 Agent 自动执行

如果使用 mock，必须明确标记。

---

## 第十九条：成本纪律

所有架构决策需要考虑：

- API cost
- Token cost
- Compute cost
- Storage cost
- Third-party service cost
- Operational complexity

禁止在没有明确收益的情况下无限增加模型调用或 Agent 层级。

---

## 第二十条：优先修复根因

出现问题时：

优先寻找根因，而不是不断增加 workaround。

允许短期 workaround，但必须明确标记：

**TEMPORARY**

并说明其存在原因。

---

# 项目主要规章制度

## Rule 1 — 一个任务，一个核心目标

每个开发任务必须有一个可以明确验证的核心目标。

如果一句话无法说清楚任务目标，说明任务范围可能过大。

## Rule 2 — 每次修改尽量最小化

默认策略：

> Minimum Necessary Change

只修改完成当前目标所必需的内容。

## Rule 3 — 先看现场，再看代码

排查线上问题时：

1. 看进程
2. 看日志
3. 看环境
4. 看真实请求
5. 再看代码

禁止仅根据代码猜测线上状态。

## Rule 4 — 禁止无证据判断

以下表达必须谨慎：

- “已经好了”
- “这个能用了”
- “部署成功”
- “Agent 支持这个”
- “API 正常”

没有实际验证，不允许下结论。

## Rule 5 — Blocker 优先

如果存在阻止核心链路运行的问题：

所有非 blocker 工作默认降级。

## Rule 6 — 不因为发现新问题而失去主线

新问题进入：

**Issue / Backlog / Follow-up**

除非它阻止当前任务，否则继续当前主线。

## Rule 7 — 不重复造轮子

现有系统如果能够可靠解决问题，不新增另一套系统。

## Rule 8 — 不提前优化

没有数据证明存在性能瓶颈，不进行大规模性能重构。

## Rule 9 — 不提前扩容

没有真实负载，不为假设中的百万用户设计系统。

## Rule 10 — 每个阶段必须留下事实记录

重要阶段至少记录：

- Current state
- What changed
- Evidence
- Remaining issues
- Next blocker

避免后续 AI 或开发者重新猜测整个系统。

---

# AI 防跑偏协议

每次 AI 准备执行较大任务前，必须内部检查：

### 1. 这是不是当前核心目标？

如果不是，停止扩大范围。

### 2. 当前任务是否直接帮助真实执行？

如果不是，降低优先级。

### 3. 我是否在假设系统状态？

如果是，先检查。

### 4. 我是否准备重构超过必要范围？

如果是，缩小修改范围。

### 5. 我是否已经有验证方法？

如果没有，先定义验证方式。

### 6. 我会不会把“代码存在”误认为“功能存在”？

如果会，必须实际运行验证。

### 7. 当前有没有更短路径？

如果有，优先短路径。

---

# 偏航判定

出现以下任意情况时，视为项目可能正在跑偏：

- 连续开发大量功能但没有真实执行验证
- UI 进度明显快于核心能力进度
- 文档中的能力远多于运行中的能力
- 不断重构但用户能力没有增加
- 不断引入新服务
- 不断增加 Agent 层级
- 工程复杂度快速增长
- 核心闭环仍然没有跑通
- 大量讨论未来规模但当前功能不稳定
- 团队无法准确回答“现在真实能做什么”

触发偏航后：

> **停止扩展 → 审计运行状态 → 找到核心 blocker → 恢复最短执行链路。**

---

# 决策优先级

当两个目标冲突时，按以下顺序决策：

**真实运行 > 功能实现 > 稳定性 > 扩展能力 > UI > 架构优雅 > 文档包装**

**核心闭环 > 功能数量**

**证据 > 推测**

**简单 > 复杂**

**当前真实需求 > 假设中的未来需求**

**解决 blocker > 新功能**

---

# 宪法修改规则

本文件不是普通开发文档。

任何 AI、Codex 或开发者不得自行修改核心原则。

只有项目负责人可以修改：

- 项目最高目标
- 优先级体系
- 完成定义
- 范围约束
- 核心开发原则

普通技术细则可以根据系统实际情况更新，但不得与上述原则冲突。

---

# 最终原则

当不知道下一步应该做什么时，回到三个问题：

> **现在真实运行的是什么？**

> **距离用户真正完成一次任务，还差哪一步？**

> **解决这个问题的最短路径是什么？**

然后只做那一步。
