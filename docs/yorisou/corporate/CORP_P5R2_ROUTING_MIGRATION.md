# CORP-P5R2 — corporate locale routing: Preview mechanism and Production migration

Status: **Preview only.** Nothing in this document has been applied to Production.
Branch: `product/corporate-p5r2-global-site`. Base: `c733e51`.

## 1. What the Preview does today

The six corporate routes carry locale in a **query parameter**:

```
/                     -> Japanese (default; no parameter)
/?lang=ar             -> Arabic
/company?lang=ru      -> Russian
```

`proxy.ts` resolves `?lang` against the locale registry for exactly these six paths — `/`,
`/mirai-move`, `/kakari`, `/about`, `/company`, `/contact` — and writes `x-yorisou-locale`.
`app/layout.tsx` reads that header and sets `<html lang>`, `dir` and `data-script` from the
registry. Every in-page link is generated by `localeHref`, so the selected language survives
navigation across the whole corporate surface.

Locale is **non-sticky**: the header and cookie are rewritten on every matched request, so a later
plain `/` returns to Japanese. Choosing a language never silently becomes a persistent preference,
and nothing is inferred from browser language, IP, device or geography.

## 2. Why not `/{locale}/...` in this package

The intended Production doctrine is `/` for Japanese and `/{locale}/...` for every other language.
That could not be implemented on this branch, for two evidenced reasons.

**`/en` is an existing legacy consumer route.** `app/en/page.tsx` is live today and is not part of
the corporate site. A corporate `/en` would collide with it directly, and `proxy.ts` still derives
consumer locale from the pathname (`pathname.startsWith("/en")`). Repointing `/en` is a consumer
product decision, not a corporate-site decision, and is out of scope here.

**A root-level `[locale]` catch-all re-breaks the 404.** A segment such as `app/[locale]/page.tsx`
matches *every* unmatched top-level path, so unknown URLs would stop 404-ing and start rendering a
corporate page in a default locale. That is precisely the dynamic-404 contamination remediated in
CORP-P4AR1 and CORP-P4AR2, and it would be a regression against a fix the Founder has already
accepted. See `CORP_P4AR2_DYNAMIC_404_AND_ROBOTS_REMEDIATION.md`.

The query parameter has neither problem: it is collision-free, it touches no consumer route, and it
leaves the 404 behaviour exactly as CORP-P4AR2 left it.

## 3. Indexability

`/?lang=xx` URLs are **not** presented as canonical or indexable. No canonical tag and no `hreflang`
set is emitted for them, because the canonical Production form is the path-based one that does not
exist yet. Emitting `hreflang` for URLs that are scheduled to change would teach search engines a
URL shape we intend to retire.

`robots.ts` and the sitemap are **untouched** by this package.

## 4. Production migration (NOT performed here)

1. Decide the disposition of the legacy consumer `/en` route — retire, move, or namespace it. This
   is a consumer product decision and gates everything below.
2. Introduce corporate locale segments **explicitly**, not via a root catch-all: generate the six
   corporate routes per locale, or scope a catch-all beneath a dedicated corporate segment so it
   cannot shadow unknown top-level paths.
3. Re-run the dynamic-404 isolation checks from CORP-P4AR2 and confirm unknown paths still 404 with
   the corporate shell, including a dynamic route such as `/connect/pair`.
4. Emit canonical + `hreflang` for the path-based URLs once they are the real ones.
5. Add `/{locale}/...` to the sitemap and re-check `robots.ts` prefix rules for the new shape.
6. 301 `/?lang=xx` -> `/{locale}/...` so any shared Preview link keeps working.

## 5. Registry is the source of truth

Adding a language requires **no change to routing code**. `app/_corporate/i18n/locales.ts` holds the
code, endonym, direction, script and publication status; `proxy.ts` and `layout.tsx` both resolve
through it. The architecture is deliberately open-ended — there is no `SUPPORTED_LANGUAGES` constant
and no hardcoded locale list anywhere in the routing path.
